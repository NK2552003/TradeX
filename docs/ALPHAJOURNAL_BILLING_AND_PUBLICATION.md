# alphajournal billing, moderation, and publication handoff

## Current implementation

The Flutter client reads the published pricing catalogue from `pricing_catalogues` in Supabase. The published JSON supplies card prices, comparison rows, feature text, and the four enforced quota values. The Free, Pro, and Business cards map to the existing backend tiers `free`, `premium`, and `enterprise`; Business is the customer-facing name for the existing enterprise tier. An administrator can edit and publish the catalogue in Admin Publishing. The live project now has one published catalogue with Business at ₹999/month or ₹11,988/year. Configured clients show a load error if that row becomes unavailable instead of inventing prices.

The client and live database enforce limits for saved notes, journal entries, live playbooks, and monthly AI requests. The migration also prevents a normal user from changing their own role or subscription tier. Community posts and comments enter `pending`; public reads require `approved`, and admins have a review queue. The live policy readback confirmed four quota triggers, an admin-only subscription write policy, and no self-write subscription policy. Complete signed-in user and admin scenario tests before treating these checks as end-to-end proof.

On Android and iOS, `RevenueCatBilling` initializes from the publishable API key in `.env`, identifies the signed-in Supabase UUID, retrieves offerings and customer info, opens the paywall for entitlement `tradex_pro`, restores purchases, and opens Customer Center. The mobile purchase UI requires current offering packages for `monthly` and `annual` only. Paid access in Supabase changes only when the server webhook reconciles the current RevenueCat subscriber record. No client callback can mark a subscription paid. Debug builds use `REVENUECAT_TEST_API_KEY`; release builds require their platform's production public key. The test key cannot be used for a Play Store or App Store launch.

Desktop Business checkout is wired to `create-business-checkout` and `razorpay-webhook`, but the published catalogue still marks Business as unavailable until the server secrets, functions, and webhook are deployed and tested. The supplied Razorpay value is a **test key ID**, not a secret. The selected test plans are ₹999 each month (`plan_TsknGQ50Mgmdgm`) and ₹11,988 each year (`plan_TskpjHZiPVrRcP`). Business annual billing has no annual discount. The checkout function compares the Razorpay plan price with the published catalogue, creates a hosted subscription link, and saves a pending intent. Only a signed webhook can reconcile provider state and grant Business access. Never enable the Business paid button merely because the public key ID exists.

## Obtain the missing test credentials

Use **Test Mode** throughout these steps. Keep the existing public Razorpay Key ID and RevenueCat Test Store SDK key in the ignored Flutter `.env`; no additional public key needs to be pasted into chat.

1. **Razorpay API Key Secret:** Sign in to the Razorpay Dashboard, switch to **Test Mode**, then open **Account & Settings → API Keys → Generate Key**. Copy the **Key Secret** when it appears; Razorpay does not show the same secret again. The Key ID should correspond to the existing test Key ID. Store the secret only in Supabase Edge Function Secrets as `RAZORPAY_SECRET_KEY` (the functions also accept `RAZORPAY_KEY_SECRET`) and store the matching ID there as `RAZORPAY_KEY_ID`. Never put either secret variable in the root Flutter `.env` asset.
2. **Razorpay Business plans:** In Test Mode open **Subscriptions → Plans → New Plan**. Create one INR monthly Business plan and one INR yearly Business plan with amounts matching the published Supabase pricing catalogue. Copy each `plan_...` ID. Store them as `RAZORPAY_BUSINESS_MONTHLY_PLAN_ID` and `RAZORPAY_BUSINESS_YEARLY_PLAN_ID` in Supabase Edge Function Secrets. Razorpay plans cannot be edited after creation, so verify the billing amount and frequency before saving.
3. **Razorpay webhook secret:** Open **Account & Settings → Webhooks** in Test Mode, create a webhook for the deployed Razorpay Edge Function URL, select subscription activation, charge, cancellation, and failure events, and set a new long random webhook secret. Save the same value in Supabase Edge Function Secrets as `RAZORPAY_WEBHOOK_SECRET`. This is a secret **you create** in the webhook form, separate from the API Key Secret. A webhook must validate `X-Razorpay-Signature` against the raw body before changing access.
4. **RevenueCat server API key:** In the RevenueCat project open **Project settings → API keys → New secret API key**. Select **v2** and grant read permissions for entitlements, customer active entitlements, and customer subscriptions. Store it as `REVENUECAT_SECRET_API_KEY` in Supabase Edge Function Secrets, and set `REVENUECAT_PROJECT_ID` to the project ID from RevenueCat. The supplied `test_...` SDK key stays in Flutter and cannot replace this server key. The separate v1 key is valid but the webhook uses v2.
5. **RevenueCat webhook token:** Create a long random token yourself. Store it as `REVENUECAT_WEBHOOK_TOKEN` in Supabase Edge Function Secrets. In **RevenueCat → Integrations → Webhooks**, set the deployed `revenuecat-webhook` URL and Authorization header to `Bearer <the same token>`. Select sandbox events for test purchases.
6. **Supabase access:** Sign in to the Supabase project Dashboard with Owner or Administrator access. Open **Edge Functions → Secrets**, add the server values above, and save. Supabase provides `SUPABASE_URL` and a privileged server key to deployed functions; never put that key into the Flutter `.env`. Apply the database migrations and pricing seed in the Dashboard SQL Editor, then deploy the Edge Functions. A public/anon key cannot perform these steps.

After the server code and functions are deployed, run test transactions and verify the **same signed-in Supabase user** gains or loses the appropriate tier only after the verified provider event. Test keys and test products never enable real-money production billing. For release, repeat setup with separate live Razorpay keys/plans/webhook and production platform-specific RevenueCat public keys and store products.

Deploy `create-business-checkout` with normal Supabase JWT verification and `razorpay-webhook` with JWT verification disabled, because Razorpay authenticates through the webhook HMAC. After a successful test payment and database readback, an admin may edit the published Business plan to set `is_purchasable` to `true` and update its CTA, FAQ, and preview text. Keep it disabled if the server returns a configuration or plan-price error.

## RevenueCat setup

1. In RevenueCat, create entitlement `tradex_pro`.
2. In Google Play Console and App Store Connect, create distinct products for monthly and yearly subscriptions. Enter the exact store product IDs in RevenueCat; product ID strings alone are not enough until the stores approve and return the products.
3. Attach both products to `tradex_pro`, then add `monthly` and `annual` packages to the **current offering**. Build a paywall for that offering and configure Customer Center.
4. Set publishable keys in the local ignored `.env`: `REVENUECAT_TEST_API_KEY` for development, `REVENUECAT_ANDROID_API_KEY` and `REVENUECAT_IOS_API_KEY` for release. `RAZORPAY_TEST_KEY_ID` is a public identifier only.
5. Configure `REVENUECAT_WEBHOOK_TOKEN` and `REVENUECAT_SECRET_API_KEY` as Supabase Edge Function secrets, together with the project's service role key. Set RevenueCat's webhook Authorization header to `Bearer <REVENUECAT_WEBHOOK_TOKEN>`. Deploy `supabase/functions/revenuecat-webhook` without JWT verification because RevenueCat is not a Supabase user. Do not use the anon key for this function.
6. Test purchase, restore, renewal, cancellation, expiry, refund, and account switching. Verify `subscriptions`, `profiles.subscription_tier`, and the limit trigger after each event. Record the event ID and do not publish until readback passes.

Install/refresh dependencies with `flutter pub add purchases_flutter purchases_ui_flutter`. The code uses the SDK methods `Purchases.configure`, `Purchases.logIn`, `Purchases.getCustomerInfo`, `Purchases.getOfferings`, `RevenueCatUI.presentPaywallIfNeeded`, `Purchases.restorePurchases`, and `RevenueCatUI.presentCustomerCenter`. Android `MainActivity` extends `FlutterFragmentActivity` for paywall UI.

The webhook currently reconciles the RevenueCat subscriber on each event. It returns an error when server secrets, profile, or RevenueCat API state are missing, which causes RevenueCat to retry. The server must be deployed and exercised in test mode before paid plans can be advertised as available. Reconcile existing purchasers once at deployment because a webhook only processes delivered events.

## Supabase deployment and verification

1. Back up the live database and inspect the current migration ledger. Apply migrations through `033` in order, then `034_public_pricing_and_community_review.sql`, `035_community_comment_reactions.sql`, and `036_billing_providers_and_user_quota.sql`. The `029_storage_buckets_setup.sql` file is separate from this migration.
2. Apply `database/rls_policies.sql` after migrations as the repository instructs. It contains the matching approved-only community read policies.
3. Run `database/seeds/04_pricing_catalogue.sql` with an authenticated database administrator. This publishes the catalogue used by the app. The Supabase anon key cannot do this.
4. From an anon session, verify exactly one published pricing row is readable. From a normal user session, verify pricing writes, paid-tier updates, and direct subscription writes are denied. Create a post and comment and verify a different normal user cannot see them. Approve each from Admin Publishing, then verify public visibility. Reject another and verify it remains hidden.
5. Use test emails you control with Supabase Auth. Create one customer and one admin only through the administrator console or privileged tooling. Never create a test admin by writing an unverified role in the client. Confirm role changes, moderation and subscription writes through the actual deployed RLS policies.

The public Supabase key can read published rows but cannot migrate tables, insert the seed, configure Edge Function secrets, or create verified admin users. A server secret key is now present in the ignored `supabase/functions/.env` file and authenticated for a REST read, but it is not a Supabase Management API credential or a database connection for DDL/deployment. Apply migrations and deploy functions through an authenticated project dashboard or CLI session. Do not put server secret keys in the Flutter `.env`, the asset bundle, chat, or source control.

## App store release gate

Current code is **not ready to upload as a production paid app**. The Android package and iOS/macOS bundle IDs still contain `com.example.tradex`; the Android release build still uses debug signing; production RevenueCat keys and store products are missing; the live catalogue and webhook have not been deployed and verified; the legal Word documents still contain business identity/contact placeholders. Complete the Google Play Data Safety, privacy URL, account deletion URL, content rating, screenshots, support contact, financial feature declarations, store billing review, and internal testing track before production release.
