# Private messaging, push delivery, and mobile dock

## What is implemented

New direct/group message bodies, shared-reference details, rich card fields, and uploaded image/document/voice bytes are encrypted on the sending client. The hosted Supabase copilot workspace is encrypted on the client, including chat history, voice transcripts, memories and saved workspace pages. The server stores authenticated ciphertext. Message edits stay encrypted; there is no plaintext retry path. Database triggers reject old clients trying to write plaintext after deployment.

Each account has an immutable X25519 identity. Per-message random AES-256-GCM keys are wrapped for the sender and each current participant using X25519 + HKDF-SHA256 + AES-256-GCM. Each complete envelope is signed with Ed25519 using a separately derived signing key, so a group recipient cannot impersonate the sender by rewriting the shared ciphertext. Routing/sender context is authenticated. Keys are stored in platform secure storage; the database only holds public keys and a passphrase-encrypted recovery backup. Recovery uses PBKDF2-HMAC-SHA256, 600,000 iterations, a random 32-byte salt and authenticated owner binding. A recipient must set up their identity before receiving new encrypted messages. New group members cannot decrypt earlier messages.

This is a versioned application encryption implementation, **not an independently audited Signal/MLS implementation**. It does not provide forward secrecy, post-compromise recovery or a key-transparency service. Public keys use trust on first use and local pinning. A malicious server at first contact, compromised application delivery, an unlocked endpoint, or a compromised device remains outside this protection. A forgotten passphrase plus loss of all device keys is unrecoverable. No server-side reset is offered that silently replaces an identity.

AI requests are sent over TLS to the Edge gateway/provider so the model can process them. **AI inference is not end-to-end private from the gateway/provider.** Hosted history is client-encrypted and Responses requests set `store: false`; provider retention rules still apply. The legacy `ai-chat` endpoint no longer writes prompts, answers, source excerpts or prompt-derived titles. The separately configured `COPILOT_API_URL` server still uses its existing server-managed encryption at rest and is not client-key E2EE.

Historical plaintext, old attachment objects, database backups, prior AI-provider records, public community posts, notes outside the copilot workspace, public market analysis and routing metadata are not retroactively encrypted by this migration. Reactions, membership, timestamps and delivery state remain metadata. Do not market this as "everything is unreadable to everyone." Historical conversion needs a separate client-driven migration after participants have keys, plus a retention plan for backups. Nothing is destructively deleted here.

The Community desktop sidebar shows the real notification control near the top. Community and Settings use the same persisted notification preferences. Push uses Web Push on browsers and FCM on Android/iOS/macOS. Windows/Linux native clients direct users to the browser. All notification previews are generic and contain no chat text. Expired subscriptions are removed; temporary delivery failures retry up to six times. Category preferences and quiet hours are evaluated at delivery; the device UTC offset is refreshed at app startup. Notifications open/focus the app, without exposing message contents or identifiers in a URL.

The mobile shell consumes the full floating dock clearance for every active page, including fixed bottom controls. Child pages receive the consumed inset, avoiding duplicate dock padding. The dock retains backdrop blur with a transparent background and no opaque shadow.

## Deployment order (required before shipping the client)

1. Review and apply `supabase/migrations/20261115014637_private_messaging_and_web_push.sql` to a staging database with the existing schema/migrations. It adds identity, subscription and delivery tables plus triggers. It rejects plaintext writes by old clients; coordinate the client rollout. Run Supabase security advisors and verify the resulting RLS/grants on the actual project. The application now requires encryption setup before private account screens open.
2. Deploy `push-dispatch`, the updated `ai-chat`, and `ai-gateway`. The dispatcher disables gateway JWT checking only because it requires a separate `x-push-secret` scheduler secret. Never put that secret or any service-role/provider credentials in Flutter build variables.
3. Web: generate a VAPID pair using the maintained `web-push` package. Store `WEB_PUSH_PRIVATE_KEY`, `WEB_PUSH_PUBLIC_KEY`, `WEB_PUSH_SUBJECT` (a monitored `mailto:` address) and a random `PUSH_DISPATCH_SECRET` as Edge Function secrets. Build Flutter web with `--dart-define=WEB_PUSH_PUBLIC_KEY=<public-key>` and deploy `push_notifications.js` and `push-sw.js` alongside the bundle. HTTPS is required. The worker's `/push/` scope deliberately avoids replacing Flutter's root worker.
4. Native: configure a Firebase project and matching Android/Apple apps. Enable FCM HTTP v1 and store a restricted Firebase service account JSON as the Edge secret `FIREBASE_SERVICE_ACCOUNT`. Supply the matching non-secret `FIREBASE_API_KEY`, `FIREBASE_APP_ID`, `FIREBASE_MESSAGING_SENDER_ID`, `FIREBASE_PROJECT_ID`, and Apple `FIREBASE_IOS_BUNDLE_ID` as Dart build defines. Apple builds also require the Push Notifications capability, appropriate `aps-environment` entitlement/provisioning profile and an APNs key uploaded to Firebase. Enable the Remote notifications background mode in Xcode when background processing is required. These account/signing steps cannot be manufactured by source code. Test on physical devices. The SDK's supported FCM token compatibility API is used; switching to newer FID delivery must update both client and dispatcher together.
5. Configure a scheduler to POST to `/functions/v1/push-dispatch` every minute with the `x-push-secret` header. See `scripts/configure_push_cron.sql` for a Supabase Cron + Vault example. Delivery is queued at notification creation and normally starts on the next scheduler tick. No schedule or provider secrets are provisioned automatically by the schema migration.
6. Test with two real accounts and a restored second device: create identities, send/edit text, image, document, chart, trade setup and voice messages, reload and verify readable content. Inspect database/storage to confirm only ciphertext is written. Verify incorrect passphrases, unavailable recipient identities, changed keys and membership failures do not send plaintext. Verify denied notification permission, toggling off, logout/account switching, background/closed-app delivery, quiet hours and expired subscriptions.
